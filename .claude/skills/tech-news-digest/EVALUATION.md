# tech-news-digest 出力品質評価フレームワーク

skill のプロンプト改善の効果を再現性のある指標で測定し、次のチューニングに活かすためのドキュメント。

---

## 何を測るか

### 1. 重要記事選定の再現率 (客観)

**定義**: 評価者が人手で「重要 5 件」を選んだリストと、skill が Stage 2 で選定したリストの overlap 率。

**計算式**:

```
再現率 = |人手選定 ∩ skill 選定| / |人手選定|
```

**許容範囲**: 0.6 以上 (5 件中 3 件以上が一致) を合格とする。

**測定手順**:

1. skill 実行前に評価者が D1 から同じ期間の記事一覧を手元で確認し、独立して 5 件を選定してメモ
2. skill 実行後、`## サマリ` セクションの選定記事リストと照合
3. URL で突合し、一致件数を数える

---

### 2. 要約の事実整合性 (主観)

**定義**: skill が生成した 1〜2 文の要約が、WebFetch で取得した本文の内容と矛盾していないかを評価者が確認する。

**スケール**: 各記事ごとに 3 段階で評価し、全選定記事の平均を出す。

| スコア | 意味                        |
| ------ | --------------------------- |
| 2      | 矛盾なし / 本文を正確に反映 |
| 1      | 一部不正確または情報が欠落  |
| 0      | 明確な事実誤認あり          |

**許容範囲**: 平均 1.5 以上。

---

### 3. トレンド抽出の意味性 (主観)

**定義**: `## トレンド (横断)` セクションが、頻度語の列挙ではなく意味的な解釈・洞察になっているかを評価する。

**スケール**: 1〜5 の 5 段階。

| スコア | 意味                                                     |
| ------ | -------------------------------------------------------- |
| 5      | 複数カテゴリ横断の関連性が示され、業界動向が明確に見える |
| 4      | 概ね洞察的だが一部キーワード羅列がある                   |
| 3      | 洞察と羅列が混在                                         |
| 2      | ほぼキーワード羅列                                       |
| 1      | 単純な単語カウントの列挙                                 |

**許容範囲**: 3 以上。

---

### 4. WebFetch 失敗率 (客観)

**定義**: Stage 3 の deep モード実行時に、WebFetch が失敗して `(summary based)` で処理された記事の比率。

**計算式**:

```
WebFetch 失敗率 = (summary based) がついた記事数 / Stage 2 選定記事数
```

ただし `webfetch_blocklist` 登録済みホスト (`openai.com`, `medium.com`) による `(summary based)` はカウントから除外する。

**許容範囲**: 0.3 未満 (30% 未満) を合格とする。

---

### 5. 同一ホスト連続 fetch 違反数 (客観)

**定義**: Stage 3 で「同一ホストへの連続 fetch は行わない」ルールに違反したバッチの数。WebFetch の実行ログ (Claude の思考過程) から確認する。

**計算式**: 連続して同じホストへの fetch が発生したケースの数 (0 が理想)。

**許容範囲**: 0 件 (ゼロトレランス)。

---

### 6. 重複記事数 (客観)

**定義**: Stage 1 の URL de-dup 処理後に残った同一 URL の重複記事数。skill の出力の `## カテゴリ別件数` 合計と、de-dup 前の `total` の差から推定できる。

**計算式**:

```
重複記事数 = de-dup 前 total - de-dup 後 total
```

**許容範囲**: 参考値として記録するのみ (de-dup が正しく動いていれば 0 になるべき)。Zenn フィードで複数 feed が同一記事を配信するため構造上発生することがある。

---

## 記録テンプレート

skill を 1 回実行するごとに `runs.md` に追記する。

```markdown
## <YYYY-MM-DD> (<mode>, <since>)

| 項目                             | 値                   |
| -------------------------------- | -------------------- |
| 実行日時 (JST)                   | YYYY-MM-DD HH:MM     |
| mode                             | deep / quick / trend |
| since                            | today / week / month |
| category フィルタ                | (なし / ai / jp ...) |
| D1 total (de-dup 前)             | N 件                 |
| D1 total (de-dup 後)             | N 件                 |
| Stage 2 選定数                   | N 件                 |
| WebFetch 失敗数 (blocklist 除く) | N 件                 |
| WebFetch 失敗率                  | X.XX                 |
| 同一ホスト連続違反数             | N 件                 |
| 重要記事再現率                   | X.XX (N/5)           |
| 要約事実整合性 (平均)            | X.X / 2.0            |
| トレンド意味性スコア             | N / 5                |
| 総合所感 (1〜5)                  | N                    |
| メモ                             | 自由記述             |
```

---

## 改善フィードバックループ

```
SKILL.md 修正
    ↓
skill 実行 (deep mode, --target=remote)
    ↓
runs.md に結果を記録
    ↓
各指標を前回と比較
    ↓
改善 or 退行を確認 → SKILL.md の次の修正ポイントを決める
    ↓
(繰り返し)
```

### チューニング優先度の目安

| 指標                  | 退行 (要対応) | 改善の対象プロンプト箇所        |
| --------------------- | ------------- | ------------------------------- |
| 重要記事再現率 < 0.6  | 即時対応      | Stage 2 の選定基準テキスト      |
| WebFetch 失敗率 ≥ 0.3 | 次回修正      | Stage 3 の blocklist / fallback |
| トレンド意味性 < 3    | 次回修正      | Stage 4 の分析視点テキスト      |
| 要約整合性 < 1.5      | 即時対応      | Stage 3 の要約生成プロンプト    |
| 同一ホスト違反 > 0    | 即時対応      | Stage 3 のバッチ計画説明        |
